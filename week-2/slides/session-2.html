Part 1

Frontend History

Let us trace how developer pain points shaped modern frameworks.

Era 1: Static Documents

  • Early websites were mostly linked HTML documents
  • Styling was basic and interaction was minimal
  • Each navigation triggered full page reload

Era 2: Server Rendered Dynamic Pages

  • Templating on server produced HTML per request
  • Good for SEO and straightforward hosting
  • Complex UI interactions were still difficult

AJAX Shift

  • Browsers started requesting data without full reload
  • Parts of page could update asynchronously
  • This unlocked richer app-like experiences

jQuery Era

  • jQuery simplified DOM selection and events
  • Rapid productivity for small interactive features
  • Large apps became hard to maintain with ad-hoc updates

Pain Points Before SPAs

  • Repeated server round-trips for small UI changes
  • Difficult state synchronization across pages
  • Inconsistent user experience between routes

Part 2

Rise of SPAs

SPAs optimized app-like UX by moving more rendering to the browser.

What is an SPA?

  • Single HTML shell loaded once
  • Client-side routing updates visible view
  • Data fetched from APIs as needed
  • UI updates without full page reload

Why SPAs Became Popular

  • Faster route transitions after initial load
  • Rich interactions similar to desktop apps
  • Reusable UI component architecture
  • Backend can focus on API contracts

SPA Lifecycle Visualization

MPA vs SPA Comparison

MPA Strengths

  • Straightforward SEO defaults
  • Simple deployment mental model
  • Route-level server ownership

SPA Strengths

  • Interactive UX and faster transitions
  • Component reuse and client state model
  • API-first backend compatibility

SPA Trade-offs

  • Initial bundle size can hurt first load
  • Client state complexity grows quickly
  • SEO needs extra handling in some setups
  • Routing/auth edge cases require discipline

SPA Framework Landscape

  • React: UI library with massive ecosystem
  • Angular: full framework with strong conventions
  • Vue: progressive model with smooth learning curve
  • Svelte: compile-time optimization approach

Part 3

React Fundamentals and Growth

React’s model made large UI codebases more manageable.

What is React?

  • Library for building user interfaces
  • Component-based composition
  • Declarative updates driven by state
  • One-way data flow by default

Declarative vs Imperative UI

Imperative

  • Manually select and mutate DOM nodes
  • Easy to create scattered update logic

Declarative

  • Describe desired UI for current state
  • Library handles DOM update strategy

Components as Building Blocks

function WeatherCard({ city, temp }) {
  return <h2>{city}: {temp} C</h2>;
}

Small focused components are easier to reason about and test.

Props and State

  • Props: input data passed from parent
  • State: local mutable data inside component
  • State changes trigger re-render

Unidirectional Data Flow

Hooks Snapshot

  • useState for component state
  • useEffect for side effects (API, subscriptions)
  • useMemo and useCallback for optimization

Why React Grew Fast

  • Simple component mental model
  • Strong open-source ecosystem
  • Large hiring demand and community support
  • Adaptable for web, mobile, and hybrid stacks

Ecosystem Snapshot

  • react-router-dom for routing
  • vite for fast builds and DX
  • react-query for server state
  • redux-toolkit / zustand for app state
  • jest + rtl for testing

Part 4

Virtual DOM and Reconciliation

This is one of the most important React interview and design topics.

Why Direct DOM Updates Hurt

  • Manual DOM operations are verbose and error-prone
  • Frequent layout recalculation can be expensive
  • Large apps need predictable update strategy

What is the Virtual DOM?

  • Lightweight in-memory representation of UI tree
  • React compares previous and next virtual trees
  • Applies minimal required changes to real DOM

DOM vs VDOM Visualization

Real DOM

  • Browser-rendered node tree
  • Direct mutations can be costly

Virtual DOM

  • JS object tree in memory
  • Diff first, then patch real DOM

Reconciliation Steps

  1. State/props change triggers new virtual tree
  2. React diffs old vs new trees
  3. Changed nodes are identified
  4. Minimal patch applied to real DOM

Why Keys Matter in Lists

  • Keys identify stable identity of list items
  • Bad keys cause unnecessary re-renders
  • Use persistent IDs instead of array index where possible

React Render Cycle (Simplified)

Batching and Scheduling (High Level)

  • React can batch multiple state updates
  • Reduces unnecessary intermediate renders
  • Improves perceived responsiveness in complex UIs

When React Re-renders

  • Component state changes
  • Parent renders and passes new props
  • Context value changes
  • Forced update (rare and usually avoidable)

Optimization Basics (Beginner Friendly)

  • Keep component responsibility small
  • Avoid unnecessary state duplication
  • Use stable keys in dynamic lists
  • Memoize only when profiling shows benefit

Part 5

TypeScript Touchpoint

Type safety complements React component-driven architecture.

Why TypeScript in React?

  • Catch prop and API shape mismatches early
  • Improve editor autocomplete and refactors
  • Reduce runtime bugs in growing codebases

Simple Typed Props Example

type WeatherCardProps = {
  city: string;
  temp: number;
};

function WeatherCard({ city, temp }: WeatherCardProps) {
  return <p>{city}: {temp} C</p>;
}
