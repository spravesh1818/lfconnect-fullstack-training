Part 1

Webhooks

Polling: your server asks "anything new?" on a timer. Inefficient, delayed, expensive at scale.

Webhook: the external service calls you the moment something happens. Push, not pull.

Push vs poll

Polling

  • Your code controls the schedule
  • Hits the API every N seconds
  • Wastes requests when nothing changed
  • Delay = poll interval (up to minutes)
  • Works without a public URL

Webhooks

  • Provider calls your endpoint
  • Near-instant delivery
  • Only fires when an event occurs
  • Requires a publicly reachable URL
  • Must verify the sender's signature

Real-world webhook uses

  • Stripe — payment succeeded, subscription cancelled, invoice created
  • GitHub — push event triggers your CI pipeline
  • Twilio — inbound SMS delivered to your handler
  • Shopify — order fulfilled, inventory updated
  • Clerk / Auth0 — user created, email verified
  • SendGrid — email opened, link clicked, bounced

Part 2

Stripe Fundamentals

Stripe is the payments infrastructure. You integrate once; Stripe handles card processing, fraud, compliance, and reporting.

Key Stripe concepts

  • Test mode — separate key set, fake cards, no real money. Always develop in test mode.
  • Publishable key (pk_test_…) — safe in the browser. Used to tokenise card data.
  • Secret key (sk_test_…) — server only. Never expose to clients or commit to git.
  • Webhook secret (whsec_…) — used to verify incoming event signatures.
  • PaymentIntent — Stripe's main object for a single payment attempt.

Stripe dashboard tour

  • Developers > API keys — copy your test secret key
  • Developers > Webhooks — register your endpoint URL and select events
  • Developers > Events — live log of all events sent to your endpoint
  • Payments — list of PaymentIntents and their status
  • Test card: 4242 4242 4242 4242 — any future expiry, any CVC

Stripe CLI for local dev

Your localhost is not reachable by Stripe. The CLI creates a secure tunnel.

# Install (macOS)
brew install stripe/stripe-cli/stripe

# Log in
stripe login

# Forward events to your local endpoint
stripe listen --forward-to localhost:3000/webhooks/stripe

# Trigger a test event manually
stripe trigger payment_intent.succeeded

Part 3

Receiving Events

Stripe POSTs a JSON payload to your endpoint. Respond with 200 fast — processing happens after the response.

Stripe event shape

{
  "id": "evt_1ABC…",
  "type": "payment_intent.succeeded",
  "data": {
    "object": {
      "id": "pi_1ABC…",
      "amount": 5000,
      "currency": "usd",
      "metadata": { "orderId": "order_42" }
    }
  }
}

Use event.type to route. Use event.data.object for the payload. Use metadata to link back to your DB records.

Common events to handle

  • payment_intent.succeeded — payment captured; fulfil the order
  • payment_intent.payment_failed — notify user, retry logic
  • checkout.session.completed — Checkout flow finished
  • invoice.paid — subscription renewed
  • invoice.payment_failed — subscription lapsed; downgrade access
  • customer.subscription.deleted — cancel account features

Signature verification

Anyone can POST to your webhook URL. Always verify the request is really from Stripe.

import Stripe from "stripe";
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

app.post("/webhooks/stripe",
  express.raw({ type: "application/json" }),
  (req, res) => {
    const sig = req.headers["stripe-signature"]!;
    let event: Stripe.Event;
    try {
      event = stripe.webhooks.constructEvent(
        req.body,
        sig,
        process.env.STRIPE_WEBHOOK_SECRET!
      );
    } catch {
      return res.status(400).send("Signature invalid");
    }
    // handle event...
    res.json({ received: true });
  }
);

Idempotency and the fast-ack pattern

  • Ack fast — return 200 immediately. Move work to a background queue (BullMQ). Stripe retries if you take >30 s.
  • Idempotency — Stripe may deliver the same event more than once. Check if you've already processed event.id before acting.
  • Retry schedule — Stripe retries failed deliveries over 3 days (up to ~15 attempts) with exponential backoff.
  • Store event.id — mark events as processed in your DB. Skip duplicates.
