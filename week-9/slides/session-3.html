Part 1

Software Development Lifecycle

The SDLC is the structured process a team follows to plan, create, test, and deliver software.

SDLC phases

  • Plan — define scope, timeline, and resources. What are we building and why?
  • Design — architecture, data models, API contracts, UI wireframes.
  • Develop — write code, following agreed patterns and standards.
  • Test — unit, integration, end-to-end, and UAT.
  • Deploy — release to staging, then production. CI/CD automates this.
  • Maintain — monitor, fix bugs, apply patches, iterate.

Waterfall vs Agile

Waterfall

  • Sequential phases, each fully complete before the next
  • Requirements locked at the start
  • Long delivery cycle (months to years)
  • High cost of late changes
  • Works well when requirements are very stable (hardware, compliance)

Agile

  • Iterative — deliver working software in short sprints
  • Requirements evolve with feedback
  • Ship every 1–4 weeks
  • Changes welcome; the process absorbs them
  • Best for most software products

Part 2

Scrum

Scrum is the most widely adopted Agile framework. It structures teamwork around short, time-boxed sprints with clear roles, artifacts, and ceremonies.

Scrum roles

  • Product Owner (PO) — owns the product backlog. Prioritises work based on business value and customer feedback. Decides what to build.
  • Scrum Master (SM) — facilitates the process. Removes blockers. Protects the team from distractions. Does not manage the team.
  • Developers — the people doing the work (engineers, designers, QA). Self-organising — they decide how to do the work.

Scrum artifacts

  • Product Backlog — ordered list of everything the product needs. Managed by the PO. Never truly empty.
  • Sprint Backlog — subset of the product backlog committed to for one sprint. Owned by the developers.
  • Increment — the sum of all completed backlog items at the end of a sprint. Must meet the Definition of Done.
  • Definition of Done (DoD) — shared checklist that every increment must pass (tests passing, code reviewed, deployed to staging, etc.).

Scrum events (overview)

  • Sprint — 1–4 week cycle that produces a shippable increment. Time-boxed and never extended.
  • Sprint Planning — team selects backlog items and creates a sprint goal. Capacity-driven.
  • Daily Standup — 15-minute sync: what did I do, what will I do, any blockers?
  • Sprint Review — demo increment to stakeholders. Collect feedback.
  • Sprint Retrospective — team reflects: what worked, what didn't, what to change.

Part 3

Git Collaboration Patterns

On a team, everyone works in isolation on branches and merges through pull requests. Code review is built into the flow.

Feature branch model

  • main is always deployable. No one pushes directly to it.
  • Every piece of work gets its own branch, created from main.
  • When the work is done, open a Pull Request to merge back into main.
  • The PR is reviewed, discussed, and approved before merging.
  • Delete the branch after merge to keep the repo clean.

Branch naming conventions

Consistent names make it obvious who owns a branch and what it contains.

# Format: type/short-description
feat/user-authentication
feat/room-join-flow
fix/stripe-signature-verify
chore/upgrade-nestjs-10
docs/add-api-readme
refactor/rooms-service-extract

# Optionally prefix with ticket number
feat/MEET-42-user-authentication

Types: feat (new feature), fix (bug), chore (tooling/deps), docs, refactor, test.

PR workflow and etiquette

  • Keep PRs small — under 400 lines is reviewable; over 1000 lines rarely gets reviewed well.
  • Write a description — what changed, why, how to test it. Link the ticket.
  • Self-review first — read your own diff before requesting review.
  • Reviews are about the code, not the person — be specific, suggest don't demand.
  • Respond to every comment — either resolve it or explain your reasoning.
  • Don't merge your own PR without at least one approval (unless solo project).

GitHub Issues and Projects

  • Issues — the atomic unit of work. A bug, a feature, a task. Give each a clear title, description, and acceptance criteria.
  • Labels — categorise by type (bug, feature, chore) and size (S, M, L).
  • Milestones — group issues into a sprint or release.
  • Projects — Kanban board: Backlog → In Progress → In Review → Done. Drag cards as work moves.
  • Link issues to PRs — use Closes #42 in the PR description to auto-close the issue on merge.

Conventional commits

A standard format for commit messages that machines and humans can both read.

# Format: type(scope): description
feat(rooms): add create room endpoint
fix(auth): correct token expiry check
chore(deps): upgrade nestjs to 10.3
docs(readme): add local dev instructions
refactor(users): extract password hash helper
test(rooms): add integration test for findAll

Enables automatic changelogs and semantic versioning. Used by most open-source projects.
