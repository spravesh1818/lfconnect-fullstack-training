Part 1

Why NestJS?

Express is minimal and flexible. NestJS is opinionated and structured. The bigger your team and codebase, the more NestJS pays off.

Express vs NestJS

Express

  • No enforced structure
  • You wire everything manually
  • Lightweight, minimal overhead
  • Great for small APIs and learning
  • DI, testing patterns are DIY

NestJS

  • Module-based architecture enforced
  • Built-in DI container
  • Decorators-first (@Controller, @Injectable)
  • First-class TypeScript support
  • Testing utilities built in

NestJS is Angular for the backend

  • Both use modules to group related code
  • Both use decorators to declare metadata (@Module, @Injectable)
  • Both use a DI container — you declare what you need; the framework provides it
  • Both encourage separation of concerns — controllers handle HTTP, services hold logic
  • Under the hood NestJS runs on Express (or Fastify) — you can still use Express middleware

Part 2

Core Building Blocks

Every NestJS app is built from modules, controllers, and services (providers).

Modules

A module groups everything related to one domain. Import what you need; export what others can use.

@Module({
  imports: [TypeOrmModule.forFeature([Room])],
  controllers: [RoomsController],
  providers: [RoomsService],
  exports: [RoomsService],
})
export class RoomsModule {}

AppModule is the root — it imports all feature modules.

Controllers

Handle HTTP requests. No business logic — delegate to the service.

@Controller("rooms")
export class RoomsController {
  constructor(private readonly roomsService: RoomsService) {}

  @Get()
  findAll() {
    return this.roomsService.findAll();
  }

  @Post()
  create(@Body() dto: CreateRoomDto) {
    return this.roomsService.create(dto);
  }
}

Services (Providers)

Hold business logic. Decorated with @Injectable() so the DI container can manage them.

@Injectable()
export class RoomsService {
  constructor(
    @InjectRepository(Room)
    private readonly roomRepo: Repository<Room>,
  ) {}

  findAll() {
    return this.roomRepo.find();
  }

  create(dto: CreateRoomDto) {
    const room = this.roomRepo.create(dto);
    return this.roomRepo.save(room);
  }
}

Part 3

Dependency Injection

Instead of creating instances yourself, you declare what you need. NestJS's container creates and injects them.

DI in plain terms

Without DI

class RoomsController {
  private svc = new RoomsService(
    new RoomsRepository()
  );
}
  • Tight coupling
  • Hard to test (can't swap)
  • You manage lifetimes

With DI (NestJS)

class RoomsController {
  constructor(
    private svc: RoomsService
  ) {}
}
  • Decoupled — just declare the type
  • Easy to mock in tests
  • Container manages lifetime

Provider scopes

  • Singleton (default) — one instance shared across the entire app. Fine for stateless services.
  • Request — new instance per HTTP request. Use when you need per-request state (e.g., current user).
  • Transient — new instance every time it is injected. Rare.

Default singleton is correct for 95 % of services. Only change scope when you have a reason.

Part 4

TypeORM with NestJS

TypeORM is the most popular ORM for NestJS. Entities are TypeScript classes decorated to map to database tables.

Entity definition

@Entity()
export class Room {
  @PrimaryGeneratedColumn("uuid")
  id: string;

  @Column()
  name: string;

  @Column({ nullable: true })
  description: string;

  @Column({ default: 50 })
  maxParticipants: number;

  @ManyToOne(() => User, user => user.hostedRooms)
  host: User;

  @CreateDateColumn()
  createdAt: Date;
}

TypeORM module setup

// app.module.ts
@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: "postgres",
      host: process.env.DB_HOST,
      port: 5432,
      username: process.env.DB_USER,
      password: process.env.DB_PASS,
      database: process.env.DB_NAME,
      autoLoadEntities: true,
      synchronize: true,   // dev only
    }),
    UsersModule,
    RoomsModule,
    MeetingsModule,
  ],
})
export class AppModule {}

Set synchronize: false in production; use migrations instead.

Part 5

NestJS CLI

The CLI generates boilerplate so you can focus on logic, not wiring.

# Install globally
npm i -g @nestjs/cli

# New project
nest new meeting-app

# Generate a module
nest g module rooms

# Generate controller + service in one
nest g resource users   # prompts for REST / GraphQL

# Useful flags
--no-spec    # skip test file
--flat       # no subfolder

Meeting app domain

We are building a Zoom-like application. Three core domains for now:

  • Users — register, login, profile. Entity: id, email, displayName, passwordHash, avatarUrl, createdAt
  • Rooms — persistent meeting rooms. Entity: id, name, description, maxParticipants, host (User), createdAt
  • Meetings — a live session in a Room. Entity: id, room (Room), startedAt, endedAt, participantCount
