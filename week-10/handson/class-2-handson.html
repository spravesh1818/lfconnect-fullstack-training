Week 10 - Class 2 Lab - Open session deck - Write a PRD and break it into GitHub Issues for the meeting app

Exercise 0 - Read the feature brief

You have been given the following one-paragraph feature description by your product manager:

"We need a chat feature for meeting rooms. When a host creates a room, participants who join should be able to send text messages visible to everyone in the room in real time. Messages should show the sender's display name and timestamp. Message history should be stored so that late joiners can scroll back and see what was discussed. We are not building video or audio in this feature."

Your job: turn this brief into a proper PRD.

Done when: you have read the brief and can summarise it back in one sentence without looking.
PRD Template — copy this into a GitHub Issue, Notion page, or Google Doc 
# PRD: In-Room Text Chat

## Overview
[One paragraph — what is this feature?]

## Problem statement
[What problem does this solve? Whose pain is it?]

## Goals
- [ ] [Measurable outcome 1]
- [ ] [Measurable outcome 2]

## Non-goals
- [What is explicitly NOT in scope?]
- [e.g., "No voice or video in this PRD"]

## User stories
As a [role], I want [action], so that [benefit].
1. As a participant, I want to...
2. As a host, I want to...

## Acceptance criteria
[Given / When / Then for each story]

## Out of scope / future work
- [Deferred ideas]

## Open questions
- [Anything that needs a decision before work starts]

Exercise 1 - Write the PRD (15 minutes)

Fill in the PRD template above for the in-room chat feature. Work individually or in pairs. Focus on:

  • At least 3 user stories (host, participant, late joiner)
  • Clear acceptance criteria using Given / When / Then for at least 2 stories
  • Non-goals — what are you explicitly not building?
  • 1–2 open questions — things that are unclear from the brief

Example open questions:

  • "How many messages should be stored per room? Is there a limit?"
  • "Should messages be deleted when the room is deleted?"
  • "Can participants see messages from before they joined?"
Done when: your PRD has an overview, 3+ user stories, acceptance criteria for 2+ stories, and at least 1 non-goal.

Exercise 2 - Break the PRD into GitHub Issues

Go to your meeting-app GitHub repository → Issues → New Issue. Create 4–6 issues covering the chat feature. Each issue should have:

Title: [type]: short, specific description

## User story
As a..., I want..., so that...

## Acceptance criteria
- [ ] Given... When... Then...
- [ ] Given... When... Then...

## Technical notes
(optional: data model hints, libs, approach)

Labels: feat  size:M
Milestone: Sprint 2

Suggested issue breakdown for chat:

  • feat: Message entity — store messages with roomId, userId, content, timestamp
  • feat: POST /rooms/:id/messages — send a message to a room
  • feat: GET /rooms/:id/messages — retrieve message history
  • feat: WebSocket gateway — real-time message broadcast to room participants
  • feat: Message DTO — validate content length, sanitise input
Done when: 4+ GitHub Issues exist with acceptance criteria and a label assigned.

Exercise 3 - Create a Sprint 2 milestone and link issues

  1. Go to Issues → Milestones → New milestone
  2. Name it "Sprint 2 - In-room chat" with a due date 2 weeks from today
  3. Edit each chat issue and assign it to the Sprint 2 milestone
  4. Open your GitHub Project board and add the issues to the Backlog column
Done when: all chat issues are linked to the Sprint 2 milestone and visible on the project board.

Exercise 4 - Present your PRD (5 minutes, stretch)

Take turns (2 minutes each group) presenting your PRD to the class. Cover:

  1. The problem statement in one sentence
  2. Your 3 user stories (read them out)
  3. One open question you identified

The rest of the class: listen for missing acceptance criteria, unclear non-goals, or open questions not raised.

Done when: each group has presented and received at least one piece of feedback from the class.

Common PRD mistakes to avoid

  • Solution-first writing — "We will use WebSockets" is implementation. The PRD should say "Messages appear in real time" — the how is for engineers to decide.
  • Missing the "so that" — a user story without a benefit is just a task. The benefit tells you how important the story is.
  • Acceptance criteria that are vague — "messages appear" is not testable. "Messages from the last 100 exchanges load within 2s" is testable.
  • No non-goals — without explicit scope limits, every meeting becomes a negotiation about what's included.
Practice: Swap PRDs with another group and do a "PRD review" — add comments or questions to their document, just like a code review but for requirements.
