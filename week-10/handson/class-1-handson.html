Week 10 - Class 1 Lab - Open session deck - Part A: secure the meeting-app API with JWT auth and a host-only guard. Part B: a short sprint planning warm-up.
Part A - Secure the API - Implement auth on your meeting-app NestJS repo. Work on a feature branch.

Exercise 1 - Install auth dependencies

npm i @nestjs/passport passport passport-jwt @nestjs/jwt bcrypt
npm i -D @types/passport-jwt @types/bcrypt

Add a JWT_SECRET to your .env (any long random string) and register JwtModule with it in your AuthModule.

Done when: the packages install and the app still boots with npm run start:dev.

Exercise 2 - Hash passwords on register, verify on login

  1. In POST /auth/register, hash the password with bcrypt.hash(password, 10) before saving the user.
  2. In POST /auth/login, look up the user, then bcrypt.compare() the candidate password. On mismatch throw UnauthorizedException.
  3. On success, sign a JWT and return { access_token }:
const payload = { sub: user.id, email: user.email, role: user.role };
return { access_token: await this.jwt.signAsync(payload) };
Done when: registering then logging in returns an access_token, and a wrong password returns 401. Confirm the stored password is a bcrypt hash, never plaintext.

Exercise 3 - JWT strategy + AuthGuard

  1. Create JwtStrategy extending PassportStrategy(Strategy). Extract the token with ExtractJwt.fromAuthHeaderAsBearerToken(), set secretOrKey from your env, and have validate() return { userId, email, role }.
  2. Protect room creation with the guard:
@UseGuards(AuthGuard('jwt'))
@Post()
create(@Req() req, @Body() dto: CreateRoomDto) {
  return this.rooms.create(dto, req.user.userId);
}
Done when: POST /rooms with no token returns 401, and with Authorization: Bearer <token> it creates a room.

Exercise 4 - RolesGuard + @Roles for host-only delete

  1. Create the decorator: export const Roles = (...roles: string[]) => SetMetadata('roles', roles);
  2. Create RolesGuard implementing CanActivate. Read the required roles with Reflector; if none are set, allow; otherwise check request.user.role.
  3. Apply both guards and the role to delete:
@UseGuards(AuthGuard('jwt'), RolesGuard)
@Roles('host')
@Delete(':id')
remove(@Param('id') id: string, @Req() req) {
  // also verify req.user.userId owns this room (ownership ≠ role)
  return this.rooms.remove(id, req.user.userId);
}
Done when: a guest token gets 403 on delete, a host token succeeds, and deleting a room you don't own is also rejected by the ownership check.

Exercise 5 - Verify with curl

# 1. log in, capture the token
TOKEN=$(curl -s -X POST localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"ada@x.io","password":"secret"}' | jq -r .access_token)

# 2. protected route without token → 401
curl -i -X POST localhost:3000/rooms -H 'Content-Type: application/json' -d '{"name":"Standup"}'

# 3. with token → 201
curl -i -X POST localhost:3000/rooms \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"name":"Standup"}'
Done when: you have reproduced 401 (no token), 201 (valid token), and 403 (wrong role on delete) from the command line.

Common auth mistakes (watch for these)

  • Storing plaintext passwords — always hash with bcrypt; never log or return the password field.
  • Putting secrets in the JWT payload — the payload is readable by anyone. It is for identity claims only.
  • Confusing 401 and 403 — no/invalid token is 401 (authn); valid token but wrong role is 403 (authz).
  • Guard order — list AuthGuard before RolesGuard so request.user exists when the role check runs.
  • Role check without ownership check — "is a host" lets any host delete any room. Also verify the caller owns this specific room.
Part B - Sprint planning warm-up - A quick ceremony rehearsal. The full ceremonies deep-dive is Class 2.

Exercise 6 - Assign roles

Split into groups of 3–4. Assign Scrum roles for this exercise:

  • Product Owner — reads the sprint goal and presents backlog items. Answers "why" questions about requirements.
  • Scrum Master — facilitates. Keeps time. Reminds the team of the process.
  • Developers (1–2) — estimate, ask clarifying questions, and commit to stories.

You have 20 minutes for this entire exercise. The SM starts a timer now.

Done when: roles are assigned and the timer is started.

Exercise 7 - Sprint goal

The PO reads the sprint goal aloud:

Sprint 1 Goal: "By the end of this sprint, a user can register, log in, and create a named meeting room via the meeting-app API."

Developers: ask any clarifying questions before estimation begins. Examples:

  • "Should rooms require a name? What's the max length?"
  • "Is email verification required for registration?"
Done when: the goal is read, questions are answered, and everyone agrees the goal is clear.

Exercise 8 - Estimate the backlog items (planning poker)

Use the Fibonacci scale: 1, 2, 3, 5, 8, 13. For each item below, everyone picks a number simultaneously (use fingers, sticky notes, or a planning poker app). Discuss and re-vote if there is a large spread.

Story 1: User registration As a new user, I want to register with email and password, so that I have an account.
AC: POST /auth/register creates user, returns JWT. Duplicate email returns 409.
Your estimate: ___
Story 2: User login As a registered user, I want to log in with email and password, so that I receive a JWT.
AC: POST /auth/login returns JWT on valid credentials. Invalid credentials returns 401.
Your estimate: ___
Story 3: Create a room As a logged-in host, I want to create a named meeting room, so that participants have somewhere to join.
AC: POST /rooms (auth required) creates room. Empty name returns 400.
Your estimate: ___
Story 4: List rooms As a user, I want to see all available rooms, so that I can choose which one to join.
AC: GET /rooms returns array of rooms with host name.
Your estimate: ___
Story 5: Delete a room (host only) As a host, I want to delete a room I own, so that abandoned rooms don't clutter the list.
AC: DELETE /rooms/:id deletes the room. 403 if requester is not the host.
Your estimate: ___

Exercise 9 - Check capacity and commit to a sprint backlog

Assume the team has 2 developers for 2 weeks. Typical capacity (at 70% focus factor): about 20–24 story points per developer, so ~40–48 total for the team.

  1. Add up your estimates for Stories 1–5
  2. Select stories to commit to, starting from Story 1 (highest priority first), until you reach your capacity
  3. Write your sprint backlog:
Sprint 1 Backlog
================
[x] Story 1 - User registration     (__ pts)
[x] Story 2 - User login            (__ pts)
[x] Story 3 - Create a room         (__ pts)
[ ] ...

Total committed: __ points
Sprint Goal: "By end of sprint, user can register, log in, and create a room."
Done when: the sprint backlog is committed to in writing with a total point count and sprint goal confirmed.

Exercise 10 - Create a GitHub Project board

  1. Go to your meeting-app GitHub repository
  2. Click Projects → New project → Board
  3. Create three columns: Backlog, In Progress, Done
  4. Create a GitHub Issue for each committed story (from your sprint backlog)
  5. Add each issue to the Backlog column
  6. Label each issue with sprint-1 and a size label (S, M, L)
Done when: the GitHub Project board has at least 4 issues in the Backlog column, each with a label and size.

Common Scrum mistakes (watch for these)

  • PO assigning estimates — only developers estimate. The PO clarifies requirements, not complexity.
  • Committing to more than capacity — it feels productive but leads to missed goals and burnout.
  • Skipping acceptance criteria — if you don't know what "done" looks like, you'll argue about it at the end of the sprint.
  • No sprint goal — a list of stories without a goal is just a to-do list. The goal aligns the team when tradeoffs arise.
