Part 1

Containers and Docker

A container packages your app and everything it needs to run — Node version, dependencies, OS libraries — into one portable unit. It runs the same on your laptop, a teammate's machine, and a cloud server.

Image vs container vs Dockerfile

  • Dockerfile — a recipe. Text file of instructions describing how to build your app's environment.
  • Image — the built result of the Dockerfile. A frozen, shareable snapshot. Like a class.
  • Container — a running instance of an image. Like an object created from a class. You can run many containers from one image.

Flow: Dockerfile → docker build → image → docker run → container.

Why bother? "It works on my machine"

  • Parity — the container that passes on your laptop is byte-for-byte the same one that runs in production. No "wrong Node version" surprises.
  • Reproducibility — anyone can run your app with one command, no 30-step setup guide.
  • Isolation — dependencies live inside the container, not polluting the host machine.
  • Deployment — Render, AWS, Google Cloud all accept a Docker image. Dockerize once, deploy anywhere.

Part 2

A Dockerfile for NestJS

We use a multi-stage build: a heavy "builder" stage compiles TypeScript, then a lean "runtime" stage ships only what's needed to run. Result: a much smaller, faster image.

Multi-stage Dockerfile

# ---- Stage 1: build ----
FROM node:20-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                 # install ALL deps (incl. dev)
COPY . .
RUN npm run build          # compile TS -> dist/

# ---- Stage 2: runtime ----
FROM node:20-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev      # prod deps only -> smaller image
COPY --from=builder /app/dist ./dist
EXPOSE 3000
CMD ["node", "dist/main.js"]

The runtime stage never sees your source or dev dependencies — only the compiled dist/.

.dockerignore — keep junk out of the image

Like .gitignore, but for the Docker build context. Without it you'd copy node_modules and secrets into the image.

node_modules
dist
.git
.env
*.log
Dockerfile
.dockerignore

Smaller build context = faster builds and a leaner, safer image.

Build and run it locally

# Build an image tagged "meeting-api"
docker build -t meeting-api .

# Run a container from it
docker run -p 3000:3000 --env-file .env meeting-api
  • -p 3000:3000 — map host port 3000 → container port 3000. Without this the app is unreachable from your browser.
  • --env-file .env — inject secrets (DB URL, JWT secret) at run time. Never bake secrets into the image.

Open http://localhost:3000 — same app, now running inside a container.

Part 3

Make the App Deploy-Ready

Two one-line changes separate "runs on my laptop" from "runs in the cloud." Hosts decide your port and expect you to read config from the environment.

Bind to the host's PORT and 0.0.0.0

// src/main.ts
const app = await NestFactory.create(AppModule);
app.enableCors();
await app.listen(process.env.PORT ?? 3000, '0.0.0.0');
  • process.env.PORT — Render (and most hosts) assign a port and inject it as PORT. Hard-coding 3000 means the host can't reach you.
  • '0.0.0.0' — listen on all network interfaces, not just localhost. Inside a container, localhost is unreachable from outside.

Config from the environment (12-factor)

  • Never hard-code secrets — DB URL, JWT secret, API keys all come from process.env.
  • Same image, different config — one image runs in dev, staging, and prod; only the env vars change.
  • .env stays out of Git — it's in .gitignore and .dockerignore. You set the real values in the host's dashboard.

Part 4

Deploy the Backend to Render

Render reads your Dockerfile straight from GitHub, builds the image, and runs it — redeploying automatically every time you push. Free tier, no credit card to start.

Create the Web Service

  1. Push meeting-app (with its Dockerfile) to GitHub.
  2. On render.com: New → Web Service → connect your GitHub repo.
  3. Render detects the Dockerfile and picks Docker as the runtime automatically.
  4. Pick the Free instance type.
  5. Add environment variables: JWT_SECRET, DATABASE_URL, etc. (Do not set PORT — Render injects it.)
  6. Click Create. Render builds the image and gives you a public https://meeting-api.onrender.com URL.

Postgres on Render

  1. New → PostgreSQL → Free plan → Create.
  2. Copy the Internal Database URL into your web service's DATABASE_URL env var.
  3. Use the Internal URL for service-to-service (faster, free); the External URL is for connecting from your laptop.

Free-tier caveats to tell students up front:

  • The web service spins down after ~15 min idle — the first request after that has a slow "cold start" (~30–60s). Normal for free tier.
  • The free Postgres database expires after ~90 days — fine for a demo, not for real data.

Part 5

Deploy the Frontend to Netlify

The React app is just static files after npm run build. Netlify serves those files on a global CDN and rebuilds on every push — free.

Connect and configure the build

  1. On netlify.com: Add new site → Import from Git → pick your frontend repo.
  2. Build command: npm run build
  3. Publish directory: dist  (Vite outputs to dist; Create-React-App uses build).
  4. Add an environment variable VITE_API_URL = your Render backend URL (https://meeting-api.onrender.com).
  5. Deploy. Netlify gives you https://your-site.netlify.app.

Wire the frontend to the backend

Read the API URL from the env var instead of hard-coding localhost:

// frontend code
const API = import.meta.env.VITE_API_URL;
fetch(`${API}/auth/login`, { ... });

SPA routing fix — a public/_redirects file so deep links and refresh don't 404:

/*    /index.html   200

Without this, refreshing on /dashboard hits Netlify looking for a file that doesn't exist. The rule sends every path to index.html and lets React Router handle it.

CORS — let the browser talk to the API

Your frontend (your-site.netlify.app) and backend (meeting-api.onrender.com) are different origins. Browsers block cross-origin requests unless the server opts in.

// src/main.ts
app.enableCors({
  origin: 'https://your-site.netlify.app',
  credentials: true,
});

Symptom when this is missing: the request fails with "blocked by CORS policy" in the browser console, even though the API works in Postman. Fix it on the backend, then redeploy.

The full picture

  Browser
     |
     v
  Netlify  (static React frontend, global CDN)
     |   fetch(VITE_API_URL)
     v
  Render   (Dockerized NestJS API)
     |   DATABASE_URL
     v
  Render Postgres

You now have a shareable public URL. Send your-site.netlify.app to anyone — friends, recruiters, your portfolio — and they can use your app live.
