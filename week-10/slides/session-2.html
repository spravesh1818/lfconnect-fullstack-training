Part 1

Product Requirements Document

A PRD describes what you are building, why, and for whom. It aligns product, engineering, and design before a line of code is written.

PRD sections

  • Overview — one paragraph summary. What is this feature?
  • Problem statement — what pain does this solve? Whose problem is it?
  • Goals — measurable outcomes. "Users can create a room in <30 seconds."
  • Non-goals — explicit scope limits. "Will not include video recording in v1."
  • User stories — who needs what and why.
  • Acceptance criteria — the bar for "done."
  • Out of scope — things explicitly deferred.

Why PRDs matter for engineers

  • Reduces back-and-forth — you know what to build before you start.
  • Prevents scope creep — non-goals are written down and agreed.
  • Basis for estimation — you can only estimate what is specified.
  • Onboarding new team members — context is captured, not lost in Slack threads.
  • Post-launch reference — what did we say this was supposed to do?

Part 2

User Stories

User stories capture requirements from the user's perspective — not the system's.

User story format

The classic three-part structure:

As a [role],
I want [action/goal],
So that [benefit/outcome].

Examples:

As a meeting host,
I want to create a named room,
So that participants know where to join.

As a participant,
I want to see who is speaking,
So that I can follow the conversation easily.

Epic → Story → Task hierarchy

  • Epic — a large body of work (multiple sprints). "User Authentication System."
  • Story — a sprint-sized unit of user value. "As a user, I want to register with email so I can log in." Fits in one sprint.
  • Task / Sub-task — technical steps inside a story. "Create UserEntity," "Build POST /auth/register," "Add bcrypt hashing," "Write integration test."

Stories deliver user value. Tasks are how engineers break down implementation.

Part 3

Acceptance Criteria

Acceptance criteria are the contract between the PO and developers. They define "done" for a specific story.

Given / When / Then format

Structured AC is unambiguous and testable.

Story: As a host, I want to create a room.

Given I am logged in as a host,
When I submit the "Create Room" form with a valid name,
Then a new room is created and I see it in my room list.

Given I am logged in as a host,
When I submit the form with an empty name,
Then I see an error: "Room name is required."

Given I am NOT logged in,
When I try to access the room creation page,
Then I am redirected to the login page.

What makes good AC

  • Testable — a QA engineer or automated test can verify it directly.
  • Specific — "user sees an error" is vague. "User sees 'Room name is required'" is specific.
  • Covers happy and sad paths — what happens when input is invalid? When the user is not logged in?
  • Written before development — not discovered during code review.
  • Agreed by both PO and developers — both sides sign off before work begins.

Part 4

Estimation

Estimation is about relative complexity, not hours. It helps the team plan sustainable sprints.

Story points (Fibonacci)

  • Points measure complexity and uncertainty, not time.
  • Use the Fibonacci sequence: 1, 2, 3, 5, 8, 13, 21. Gaps force deliberate comparison.
  • 1 — trivial (fix a typo, update a constant)
  • 3 — small feature with clear requirements
  • 5 — medium feature with some unknowns
  • 8 — complex or unfamiliar; consider splitting
  • 13+ — too big; split before putting in a sprint

Planning poker

Synchronous estimation game to surface disagreements and build shared understanding.

  1. PO reads the story aloud
  2. Team members silently pick a card (1, 2, 3, 5, 8, 13…)
  3. Everyone reveals at the same time
  4. Highest and lowest estimators explain their reasoning
  5. Discuss, then re-vote until convergence

Disagreements in estimates reveal missing requirements or different assumptions — valuable signal.

Part 5

Creating Tickets

A well-written ticket is self-contained. A developer should be able to pick it up on Monday morning with no extra context-gathering.

Anatomy of a good GitHub Issue

Title: [feat] Create room endpoint — POST /rooms

## User story
As a host, I want to create a named room
so that participants can join my meeting.

## Acceptance criteria
- [ ] POST /rooms with valid body creates room, returns 201
- [ ] POST /rooms with empty name returns 400 "name required"
- [ ] Unauthenticated request returns 401
- [ ] Room is persisted in the database

## Technical notes
- Entity: Room (name, maxParticipants, hostId, createdAt)
- Validate with class-validator DTOs
- Tests: 1 happy path + 2 error cases

Labels: feat, size:M
Milestone: Sprint 1
Estimate: 3 points

Ticketing anti-patterns

  • Monster tickets — "Build the entire auth system" is not a story. Split it.
  • Vague titles — "Fix bug" tells no one what to fix. "Fix: room creation 500 when name is null" is actionable.
  • No acceptance criteria — how will anyone know it's done?
  • Technical tasks as user stories — "Refactor database schema" is a task, not a story. Fine to track, but not a story.
  • Tickets that bypass discussion — if the requirements are unclear, write the ticket and have a refinement conversation before work starts.
