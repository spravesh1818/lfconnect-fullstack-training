Part 1

Authentication and Authorization

Anyone can hit the meeting-app routes today. By the end of this session, only logged-in users can act, and only a room's host can delete it.

Authentication vs Authorization

Authentication (authn)

  • Question: "Who are you?"
  • Proves identity — email + password, then a token
  • Happens once at login
  • Fails with 401 Unauthorized

Authorization (authz)

  • Question: "What are you allowed to do?"
  • Checks permissions — roles, ownership
  • Happens on every protected request
  • Fails with 403 Forbidden

Authn comes first; authz only makes sense once you know who the caller is.

Sessions vs tokens (why JWT)

  • Session cookies: server stores session state, sends an opaque ID. Simple, but the server must remember every session — harder to scale across many API instances.
  • JWT (JSON Web Token): the server signs a token containing the claims. It stores nothing — it just verifies the signature on each request. Stateless, which fits a horizontally-scaled API.
  • Trade-off: a JWT can't be revoked before it expires. Keep access tokens short-lived (e.g. 15–60 min); use refresh tokens for longer sessions.

Part 2

The JSON Web Token

JWT anatomy

Three Base64URL parts joined by dots: header.payload.signature

// header  — algorithm + type
{ "alg": "HS256", "typ": "JWT" }

// payload — claims (NEVER put secrets here; it's only encoded, not encrypted)
{ "sub": "42", "email": "ada@x.io", "role": "host", "iat": 1719500000, "exp": 1719503600 }

// signature = HMAC_SHA256( base64url(header) + "." + base64url(payload), SECRET )
  • The payload is readable by anyone — only the signature is secret. Don't store passwords or sensitive data in it.
  • The server trusts the token because only it knows SECRET and can reproduce the signature.
  • exp is the expiry timestamp — the guard rejects expired tokens automatically.

Never store passwords — hash them

On register, hash the password with bcrypt. On login, compare the candidate against the stored hash. The plaintext is never saved.

import * as bcrypt from 'bcrypt';

// register
const hash = await bcrypt.hash(dto.password, 10); // 10 = salt rounds
await this.users.create({ email: dto.email, password: hash });

// login
const ok = await bcrypt.compare(dto.password, user.password);
if (!ok) throw new UnauthorizedException('Invalid credentials');
  • Salt is built into the hash — two identical passwords produce different hashes.
  • bcrypt is deliberately slow, which makes brute-forcing the stored hashes expensive.

Part 3

Authentication in NestJS

Validate credentials, then sign and return a JWT the client sends back on every future request.

Login — issuing the token

// auth.service.ts
async login(dto: LoginDto) {
  const user = await this.users.findByEmail(dto.email);
  if (!user || !(await bcrypt.compare(dto.password, user.password)))
    throw new UnauthorizedException('Invalid credentials');

  const payload = { sub: user.id, email: user.email, role: user.role };
  return { access_token: await this.jwt.signAsync(payload) };
}

The client stores access_token and sends it as Authorization: Bearer <token> on protected routes.

The Passport JWT strategy

The strategy tells NestJS how to find and verify the token. Its validate() return value becomes request.user.

// jwt.strategy.ts
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: process.env.JWT_SECRET,
    });
  }
  // payload = the decoded, signature-verified JWT
  validate(payload: any) {
    return { userId: payload.sub, email: payload.email, role: payload.role };
  }
}

Part 4

Guards — the authorization layer

A guard is a class with a canActivate() method. It runs before the route handler and decides — true lets the request through, false (or a thrown exception) blocks it.

Where guards sit in the request lifecycle

Request
  → Middleware
  → Guards          ← canActivate(): allow or reject (401/403)
  → Interceptors / Pipes
  → Route handler (controller method)
  → Response
  • Guards run after middleware but before the handler — so a blocked request never touches your business logic.
  • They have access to the full execution context: the request, the handler, and its metadata (decorators).
  • Order: authentication guard first (is there a valid user?), then authorization guards (is that user allowed?).

AuthGuard — require a logged-in user

AuthGuard('jwt') runs the JWT strategy. No valid token → 401. Valid token → request.user is populated.

// rooms.controller.ts
@UseGuards(AuthGuard('jwt'))
@Post()
create(@Req() req, @Body() dto: CreateRoomDto) {
  // req.user came from JwtStrategy.validate()
  return this.rooms.create(dto, req.user.userId);
}

Apply it per-route, per-controller (@UseGuards on the class), or globally with APP_GUARD.

Role-Based Access Control

Authentication tells you the user is logged in. RBAC decides whether this user may perform this action — without it, every authenticated user can do everything.

  • Attach a role to each user (guest, host, admin) and put it in the JWT payload.
  • Tag sensitive routes with the role they require; a guard enforces the rule.

A custom RolesGuard + @Roles decorator

// roles.decorator.ts
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.get<string[]>('roles', ctx.getHandler());
    if (!required) return true;                 // no @Roles → open to any authed user
    const { user } = ctx.switchToHttp().getRequest();
    return required.includes(user.role);        // false → 403 Forbidden
  }
}

The decorator tags a route with required roles; the guard reads the tag with Reflector and checks request.user.

Putting it together on meeting-app

@Controller('rooms')
@UseGuards(AuthGuard('jwt'), RolesGuard) // authn first, then authz
export class RoomsController {

  @Get()                       // any logged-in user
  findAll() { /* ... */ }

  @Delete(':id')
  @Roles('host')               // only hosts reach the handler
  remove(@Param('id') id: string, @Req() req) {
    return this.rooms.remove(id, req.user.userId); // also check ownership
  }
}
  • Role ≠ ownership. "is a host" is RBAC; "is the host of this room" is an ownership check inside the service — do both.

Part 5

Scrum recap

A fast refresher before Class 2 goes deep on ceremonies. The auth stories above are exactly the kind of work you'll plan into a sprint.

The four ceremonies at a glance

  • Sprint Planning — team selects backlog items it can complete and commits to a sprint goal. Never plan to 100% capacity (~0.6–0.7 focus factor).
  • Daily Standup — 15-min sync: done / doing / blockers. Surface blockers here, solve them after.
  • Sprint Review — demo working software to stakeholders; adapt the backlog from feedback.
  • Sprint Retrospective — team-only; inspect the process. Start / Stop / Continue with 1–3 owned action items.

Sprint mechanics + Definition of Done vs Acceptance Criteria

  • Time-boxing: the sprint ends on schedule; unfinished work returns to the backlog. No mid-sprint scope creep.
  • Velocity: avg story points per sprint — for forecasting, never to rank individuals.

Definition of Done

  • Applies to every item; set by the team
  • The quality bar — tests pass, reviewed, deployed
  • Same every sprint

Acceptance Criteria

  • Specific to one story; set by the PO
  • The feature spec — e.g. "invalid email shows an error"
  • Different every story
