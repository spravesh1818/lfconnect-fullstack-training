Part 1

Branching Strategies

A branching strategy is a team agreement about how code flows from development to production. Pick one and be consistent.

Three main strategies

Gitflow

  • main + develop + release/* + hotfix/*
  • Structured release cycles
  • Good for versioned software (apps, packages)
  • Heavier — more merges, more branches

GitHub Flow

  • main + feature branches
  • Feature branches merge directly to main
  • Deploy from main continuously
  • Simple — good for web apps / SaaS

Trunk-based development

  • Everyone commits to main (or very short-lived branches — hours, not days)
  • Feature flags hide incomplete work from users
  • Requires strong CI — every commit must be deployable
  • Used at Google, Meta, and high-velocity SaaS teams
  • When to use: mature CI/CD, experienced team, feature-flagging infrastructure

For most student teams: GitHub Flow is the right default.

Part 2

Merge Strategies

How a PR's commits land on main affects history readability. Pick based on your team's preference.

Merge vs squash vs rebase

  • Merge commit — preserves all commits from the branch plus a merge commit. Full history, can look noisy.
  • Squash and merge — collapses all branch commits into one on main. Clean linear history; detail is in the PR, not git log.
  • Rebase and merge — replays branch commits on top of main without a merge commit. Linear history with full commit granularity. Rewrites SHA — avoid on shared branches.

Most teams pick squash or merge and enforce it with GitHub branch settings.

Resolving merge conflicts

  1. Fetch main: git fetch origin && git checkout main && git pull
  2. Switch to your branch: git checkout feat/room-join
  3. Merge main into your branch: git merge main
  4. Open conflicting files — look for <<<<<<< markers
  5. Edit to keep the correct code — remove all markers
  6. Stage resolved files: git add .
  7. Commit: git commit (Git pre-fills the merge message)
  8. Push: git push — the PR updates automatically

Part 3

Branch Protection Rules

Protect main from accidental force pushes and unreviewed code.

Recommended protection settings

  • Require pull request before merging — no direct pushes to main
  • Require approvals: 1 — at least one teammate must review
  • Require status checks to pass — CI must be green before merge
  • Require branches to be up to date — prevents merging stale code
  • Do not allow force pushes — protects history

Set in GitHub → Settings → Branches → Add branch protection rule.

PR best practices (checklist)

  • Keep PRs under 400 lines — reviewable in one sitting
  • One logical change per PR — easy to revert if needed
  • Write a description: what changed, why, how to test
  • Link the issue: Closes #42
  • Self-review your diff before requesting review
  • Respond to every comment — resolve or explain
  • Do not merge until CI is green and you have an approval

Part 4

GitHub Actions

GitHub Actions is a CI/CD platform built into GitHub. Workflows are YAML files in .github/workflows/ that run on events like push or pull_request.

Workflow anatomy

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

Key GitHub Actions concepts

  • Workflow — a YAML file triggered by an event (push, PR, schedule, manual)
  • Job — a set of steps that run on one runner. Jobs run in parallel by default.
  • Step — a single command or reusable action (uses: or run:)
  • Runner — a VM that executes the job (ubuntu-latest, macos-latest, windows-latest)
  • Actions — pre-built steps from the GitHub Marketplace (actions/checkout, actions/setup-node)

Adding a Postgres service for integration tests

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
          POSTGRES_DB: meeting_test
        ports:
          - 5432:5432
        options: --health-cmd pg_isready
    env:
      DATABASE_URL: postgresql://test:test@localhost:5432/meeting_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm test
