Part 1

Pick Your Auth Layer

Custom JWT taught you the mechanics. In industry, teams often reach for tools once the basics are understood.

Four approaches compared

Custom JWT (Week 7)

  • You own every line
  • Slowest to ship
  • Best for learning + full control

Passport.js

  • Strategy plugins for Express
  • Medium speed
  • OAuth, local, JWT strategies

Supabase Auth

  • Hosted auth + Postgres
  • Fast MVPs
  • Magic link, social login built-in

Clerk

  • Hosted auth + React components
  • Fastest UI integration
  • Dashboard, MFA, orgs

Quick decision guide

  • Learning / MERN course project — custom JWT (what you have)
  • Express + "Login with Google" — Passport + OAuth strategy
  • Startup MVP with Postgres — Supabase
  • React SaaS needing auth UI yesterday — Clerk

Part 2

Passport.js

Authentication middleware for Node. You plug in a strategy — local password, JWT, Google OAuth — and Passport standardizes the flow.

Core idea

  • Strategy — how credentials are verified
  • Serialize / deserialize — map user to session or token
  • authenticate() — middleware on a route

Passport does not replace your user model. You still store users and decide what to return (JWT, session cookie).

Local strategy snippet

import passport from "passport";
import { Strategy as LocalStrategy } from "passport-local";

passport.use(new LocalStrategy(
  { usernameField: "email" },
  async (email, password, done) => {
    const user = await UserModel.findOne({ email });
    if (!user || !await bcrypt.compare(password, user.passwordHash)) {
      return done(null, false);
    }
    return done(null, user);
  }
));

app.post("/auth/passport-login",
  passport.authenticate("local", { session: false }),
  (req, res) => {
    const token = jwt.sign({ sub: req.user.id }, JWT_SECRET);
    res.json({ token, user: req.user });
  }
);

Common Passport strategies

  • passport-local — email + password
  • passport-jwt — extract Bearer token, verify
  • passport-google-oauth20 — "Sign in with Google"
  • passport-github2 — "Sign in with GitHub"

Part 3

Supabase Auth

Backend-as-a-Service: hosted Postgres, auth, storage, realtime. Auth is one piece — but a powerful one for MVPs.

What Supabase gives you

  • Email/password, magic links, phone OTP
  • Social providers (Google, GitHub, …)
  • session object in client SDK
  • Row Level Security (RLS) — SQL policies per user

React snippet

import { createClient } from "@supabase/supabase-js";

const supabase = createClient(
  import.meta.env.VITE_SUPABASE_URL,
  import.meta.env.VITE_SUPABASE_ANON_KEY
);

// Register
await supabase.auth.signUp({ email, password });

// Login
const { data, error } = await supabase.auth.signInWithPassword({
  email, password,
});
// data.session.access_token available

When Supabase fits

  • You want Postgres + auth without managing servers
  • Magic link login is a product requirement
  • Small team shipping in weeks, not months

Tradeoff: your data and auth rules live in Supabase's platform.

Part 4

Clerk

Hosted authentication with drop-in React components — sign-in forms, user button, session management out of the box.

Clerk React setup

import { ClerkProvider, SignIn, SignUp, UserButton } from "@clerk/clerk-react";

const pk = import.meta.env.VITE_CLERK_PUBLISHABLE_KEY;

<ClerkProvider publishableKey={pk}>
  <Routes>
    <Route path="/sign-in" element={<SignIn />} />
    <Route path="/sign-up" element={<SignUp />} />
  </Routes>
  <UserButton />
</ClerkProvider>

Clerk hooks

import { useUser, useAuth } from "@clerk/clerk-react";

const { user, isSignedIn } = useUser();
const { getToken } = useAuth();

// Attach to your API
const token = await getToken();
fetch("/api/events", {
  headers: { Authorization: `Bearer ${token}` },
});

When Clerk fits

  • React/Next app needs polished auth UI immediately
  • You want MFA, orgs, and user management dashboard
  • Backend stays thin — Clerk handles identity

Part 5

Tradeoffs

Questions to ask before choosing

  • Vendor lock-in — how hard is migration later?
  • Pricing — free tier limits, per-MAU costs
  • Data residency — where are users stored?
  • Custom rules — odd login flows, legacy LDAP?
  • Team skills — can you maintain custom auth?
