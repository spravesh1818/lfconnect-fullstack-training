Part 1

REST Verbs Cheat Sheet

Each HTTP method has a job. Use the right one so your API is predictable.

CRUD mapping

  • CREATE — POST /todos
  • READ (list) — GET /todos
  • READ (one) — GET /todos/:id
  • UPDATE (full) — PUT /todos/:id
  • UPDATE (partial) — PATCH /todos/:id
  • DELETE — DELETE /todos/:id

PUT vs PATCH

PUT

  • Replace the entire resource
  • Send title and completed
  • Missing field may reset to default

PATCH

  • Update only what changed
  • Send { "completed": true } only
  • Title stays the same — mark done in one step

Status codes for CRUD

  • 200 — OK (GET, PUT, PATCH success)
  • 201 — Created (POST)
  • 204 — No Content (DELETE success, empty body)
  • 400 — Bad Request (validation failed)
  • 404 — Not Found (id does not exist)

Part 2

Validation with Zod

Never trust req.body. Validate at the HTTP boundary before touching the database.

Why validate?

  • Clients can send anything — bugs, old apps, attackers
  • Database errors are harder to read than 400 JSON
  • Same Zod library you used with react-hook-form in Week 4

Schemas + DTOs

export const createTodoSchema = z.object({
  title: z.string().min(1),
  completed: z.boolean().optional().default(false),
});

export const updateTodoSchema = createTodoSchema.partial();

export type CreateTodoDto = z.infer<typeof createTodoSchema>;

One schema → runtime validation + TypeScript type. No duplication.

Reusable validate middleware

export const validate = (schema: ZodSchema) =>
  (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ error: result.error.flatten() });
    }
    req.body = result.data;
    next();
  };

Part 3

Implement Remaining Routes

GET by id, PUT, PATCH, DELETE — all follow the same pattern: find, act, return status.

GET /todos/:id

const todo = await TodoModel.findById(req.params.id);
if (!todo) return res.status(404).json({ error: "Todo not found" });
res.json(todo);

Invalid id format → catch and return 400.

PATCH — mark complete

// Client sends only what changed
PATCH /todos/:id
{ "completed": true }

This is why todos are a great PATCH teaching example.

DELETE /todos/:id

const deleted = await TodoModel.findByIdAndDelete(req.params.id);
if (!deleted) return res.status(404).json({ error: "Todo not found" });
res.status(204).send();

204 means success with no response body.

Part 4

Domain-Driven Design (Beginner Version)

Group code by business area (todos, users, auth) — not only by technical type.

Bad: everything by layer only

src/
  controllers/   # all controllers mixed
  models/        # all models mixed
  routes/        # all routes mixed

Works for tiny apps. Gets messy when you add users, auth, notifications…

Better: modules by domain

src/
  app.ts
  server.ts
  config/db.ts
  middleware/validate.ts
  modules/
    todos/
      todo.model.ts
      todo.schema.ts
      todo.service.ts
      todo.controller.ts
      todo.routes.ts

Layer responsibilities

  • routes — URL + HTTP method → controller
  • controller — read request, call service, send response
  • service — business rules + database calls
  • model — Mongoose schema
  • schema — Zod + DTO types

Request flow after refactor

Client
  → Express (app.ts)
  → todo.routes.ts
  → validate middleware
  → todo.controller.ts
  → todo.service.ts
  → TodoModel → MongoDB

Wire routes in app.ts

import { todoRoutes } from "./modules/todos/todo.routes.js";

app.use("/todos", todoRoutes);

Each domain gets its own router. Tomorrow we add modules/auth/.
