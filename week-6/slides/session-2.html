Part 2

JavaScript → TypeScript

Same runtime (Node + Express). TypeScript catches typos before you run the server and pairs with Zod for shared DTO types.

Install tooling

npm install -D typescript tsx @types/node @types/express

tsx runs .ts files directly — no manual compile step in class.

tsconfig.json (class standard)

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noEmit": true,
    "allowImportingTsExtensions": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}

noEmit + allowImportingTsExtensions let you write import "./file.ts".

Import rules

  • Your files — use the .ts extension: from "./config/db.ts"
  • npm packages — no extension: from "express"

You edit db.ts on disk → you import db.ts in code. Same name, no guessing.

Migrate one file at a time

  1. config/db.js → db.ts
  2. models/todo.model.js → todo.model.ts
  3. server.js → server.ts
  4. Fix imports after each rename; run npm run dev often

Types to add today

  • Request, Response from Express on route handlers
  • Promise<void> on connectDB()
  • CreateTodoBody interface for req.body (replaced by Zod later)
  • Todo interface on the Mongoose model file

Typed server.ts (GET + POST)

import { Request, Response } from "express";
import { connectDB } from "./config/db.ts";
import { TodoModel } from "./models/todo.model.ts";

interface CreateTodoBody {
  title?: string;
}

app.get("/todos", async (_req: Request, res: Response) => {
  const todos = await TodoModel.find().sort({ createdAt: -1 });
  res.json(todos);
});

app.post("/todos", async (req: Request, res: Response) => {
  const { title } = (req.body ?? {}) as CreateTodoBody;
  if (!title || !title.trim()) {
    return res.status(400).json({ error: "title is required" });
  }
  const todo = await TodoModel.create({ title: title.trim() });
  res.status(201).json(todo);
});

Run with tsx

// package.json
"dev": "tsx watch src/server.ts"

Verify with curl — behavior should match Class 1. IDE should show types on req and res.

Other codebases: some teams compile to dist/ and use .js in import strings. We use .ts imports in class for clarity.

Part 3

Middleware & Zod Validation

Never trust req.body. Validate at the HTTP boundary before touching the database.

Middleware pipeline

Request
  → express.json()     // parse body
  → validate(schema)   // Zod check
  → route handler      // controller / logic

Same pattern as Week 5 meetings API.

Why validate?

  • Clients can send anything — bugs, old apps, attackers
  • Replace manual if (!title) with reusable middleware
  • Same Zod library from Week 4 forms and Week 5 backend

Schemas + DTOs

export const createTodoSchema = z.object({
  title: z.string().min(1),
  completed: z.boolean().optional().default(false),
});

export const updateTodoSchema = createTodoSchema.partial();

export type CreateTodoDto = z.infer<typeof createTodoSchema>;

One schema → runtime validation + TypeScript type. No duplication.

Reusable validate middleware

export const validate = (schema: ZodSchema) =>
  (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ error: result.error.flatten() });
    }
    req.body = result.data;
    next();
  };

Part 4

REST Verbs & Full CRUD

Each HTTP method has a job. Use the right one so your API is predictable.

CRUD mapping

  • CREATE — POST /todos
  • READ (list) — GET /todos
  • READ (one) — GET /todos/:id
  • UPDATE (full) — PUT /todos/:id
  • UPDATE (partial) — PATCH /todos/:id
  • DELETE — DELETE /todos/:id

PUT vs PATCH

PUT

  • Replace the entire resource
  • Send title and completed
  • Missing field may reset to default

PATCH

  • Update only what changed
  • Send { "completed": true } only
  • Title stays the same — mark done in one step

Status codes for CRUD

  • 200 — OK (GET, PUT, PATCH success)
  • 201 — Created (POST)
  • 204 — No Content (DELETE success, empty body)
  • 400 — Bad Request (validation failed)
  • 404 — Not Found (id does not exist)

GET /todos/:id

const todo = await TodoModel.findById(req.params.id);
if (!todo) return res.status(404).json({ error: "Todo not found" });
res.json(todo);

Invalid id format → catch and return 400.

PATCH — mark complete

// Client sends only what changed
PATCH /todos/:id
{ "completed": true }

This is why todos are a great PATCH teaching example.

DELETE /todos/:id

const deleted = await TodoModel.findByIdAndDelete(req.params.id);
if (!deleted) return res.status(404).json({ error: "Todo not found" });
res.status(204).send();

204 means success with no response body.

Part 5

Domain-Driven Design (Beginner Version)

Group code by business area (todos, users, auth) — not only by technical type.

Bad: everything by layer only

src/
  controllers/   # all controllers mixed
  models/        # all models mixed
  routes/        # all routes mixed

Works for tiny apps. Gets messy when you add users, auth, notifications…

Better: folders by domain

src/
  app.ts
  server.ts
  config/db.ts
  middleware/validate.ts
  todo/
    controller/todo.controller.ts
    routes/todo.routes.ts
    service/todo.service.ts
    model/todo.model.ts
    schema/todo.schema.ts

Layer responsibilities

  • routes — URL + HTTP method → controller
  • controller — read request, call service, send response
  • service — business rules + database calls
  • model — Mongoose schema
  • schema — Zod + DTO types

Request flow after refactor

Client
  → Express (app.ts)
  → todo.routes.ts
  → validate middleware
  → todo.controller.ts
  → todo.service.ts
  → TodoModel → MongoDB

Wire routes in app.ts

import { todoRoutes } from "./todo/routes/todo.routes.ts";

app.use("/todos", todoRoutes);

Each domain gets its own router. Tomorrow we add auth/ the same way.
