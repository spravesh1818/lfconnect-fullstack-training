Part 1

TypeScript Fundamentals

The language we will use across the rest of Week 5 — typed contracts between client, server, and database.

Why TypeScript for the backend?

  • Types describe the API contract at the boundary
  • Catch shape mismatches before they reach production
  • Confident refactors as the codebase grows
  • Same tooling and types as our React client

Install and run

# dev dependencies
npm install -D typescript tsx @types/node

# generate tsconfig.json (optional)
npx tsc --init

# run a single TS file fast
npx tsx src/server.ts

tsx executes TypeScript directly during development; tsc compiles for production.

tsconfig.json essentials

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "outDir": "dist",
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}

Start with strict: true — it forces you to handle null, undefined, and untyped inputs.

Primitives, arrays, and literal types

const name: string = "Basum";
const port: number = 3000;
const isLive: boolean = true;

const tags: string[] = ["api", "node"];

type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
const method: HttpMethod = "GET";

type vs interface

type Meeting = {
  id: string;
  title: string;
  host: string;
};

interface User {
  id: string;
  email: string;
}

// both can extend
interface Admin extends User {
  role: "admin";
}

Prefer type for unions and computed types; interface shines when extending or merging.

Unions and narrowing

type ApiResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string };

function show(result: ApiResult<Meeting>) {
  if (result.ok) {
    console.log(result.data.title);   // narrowed
  } else {
    console.log(result.error);
  }
}

Discriminated unions let TypeScript narrow types based on a tag like ok.

Generics

function ok<T>(data: T) {
  return { ok: true as const, data };
}

const meeting = ok({ id: "m1", title: "Sprint" });
// inferred: { ok: true; data: { id: string; title: string } }

Generics keep helpers reusable while preserving the caller's type.

Utility types

type Meeting = { id: string; title: string; host: string };

type NewMeeting   = Omit<Meeting, "id">;
type MeetingPatch = Partial<Meeting>;
type MeetingSlim  = Pick<Meeting, "id" | "title">;
type MeetingMap   = Record<string, Meeting>;

Inference, unknown, and any

  • Prefer letting TypeScript infer return types and locals
  • Use unknown for I/O (req body, JSON parse) and narrow before use
  • Avoid any — it silently disables type checking
const body: unknown = JSON.parse(input);
if (typeof body === "object" && body !== null) { /* narrow */ }

Part 2

Backend Foundations

What lives on the server, how a request travels, and which API style fits the job.

What is a backend?

  • Server-side code that owns business logic, persistence, and auth
  • Exposes APIs the frontend (and other services) call over the network
  • Holds secrets the client should never see (DB credentials, signing keys)

Frontend vs backend responsibilities

Frontend

  • Rendering and UX
  • Local UI state
  • Calls APIs

Backend

  • Business rules
  • Database and integrations
  • Auth, validation, security

Lifecycle of an HTTP request

  1. Browser resolves DNS for the host
  2. TCP + TLS handshake to the server
  3. Client sends HTTP request (method, URL, headers, body)
  4. Server routes to a handler and runs middleware
  5. Handler may read/write the database
  6. Server sends HTTP response (status, headers, body)
  7. Connection closed or kept alive for the next request

Anatomy of an HTTP request

POST /meetings HTTP/1.1
Host: api.basum.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{ "title": "Sprint Review", "date": "2026-06-01T10:00:00Z" }

Every request has a method, URL, headers, and optionally a body.

REST verbs

  • GET — read a resource (safe, idempotent)
  • POST — create a new resource (not idempotent)
  • PUT — replace a resource (idempotent)
  • PATCH — partially update a resource
  • DELETE — remove a resource (idempotent)

Idempotent = same request repeated yields the same end state.

HTTP status codes you will use

  • 2xx — success: 200 OK, 201 Created, 204 No Content
  • 4xx — client errors: 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict
  • 5xx — server errors: 500 Internal Server Error, 503 Service Unavailable

Types of APIs

  • REST — resource URLs, HTTP verbs, JSON bodies
  • GraphQL — single endpoint, client-specified query
  • Others (mention only): gRPC, WebSocket, tRPC, SOAP

REST in one slide

GET    /meetings           list
GET    /meetings/:id       fetch one
POST   /meetings           create
PUT    /meetings/:id       replace
PATCH  /meetings/:id       update fields
DELETE /meetings/:id       remove

Each resource has a URL; verbs describe what to do with it.

GraphQL in one slide

# single endpoint: POST /graphql
query {
  meeting(id: "m1") {
    title
    host { name }
    participants { name email }
  }
}

The client lists exactly which fields it wants — server returns only those.

REST vs GraphQL — tradeoffs

REST

  • Simple, HTTP caching by URL + method
  • Mature tooling and conventions
  • Risk of over/under-fetching, more round trips

GraphQL

  • Client picks the exact fields
  • One round trip, typed schema
  • Caching is harder, N+1 query traps

When to choose which

  • REST for straightforward CRUD, public APIs, cacheable reads
  • GraphQL when clients need nested or aggregated views and field-level flexibility
  • Don't ship both unless there is a real reason

This week we build with REST + Express.

Part 3

Express and Middleware

The most popular Node.js web framework — small surface, big ecosystem.

What is Express?

  • Thin framework on top of Node's http module
  • Provides routing, middleware, and request/response helpers
  • Stays unopinionated about validation, ORM, and project structure

Install Express

npm install express
npm install -D @types/express

The types package gives autocomplete for Request, Response, and middleware signatures.

Minimal server

import express from "express";

const app = express();
const PORT = 3000;

app.listen(PORT, () => {
  console.log(`Listening on http://localhost:${PORT}`);
});

Routes and handlers

app.get("/meetings", (req, res) => {
  res.json([{ id: "m1", title: "Sprint" }]);
});

app.post("/meetings", (req, res) => {
  res.status(201).json({ id: "m2", ...req.body });
});

Each route maps a method + path to a handler function.

Working with req and res

// URL path params       /meetings/:id
req.params.id

// query string          /meetings?host=alice
req.query.host

// parsed JSON body
req.body

// send a response
res.status(201).json({ ok: true });

Middleware mental model

  • A middleware is a function: (req, res, next) => void
  • It can read/modify req/res, then call next() to continue
  • Requests flow through middleware in order until a handler responds
app.use((req, _res, next) => {
  console.log(req.method, req.url);
  next();
});

Built-in middleware

app.use(express.json());          // parse JSON bodies
app.use(express.urlencoded({ extended: true })); // form bodies

Without express.json(), req.body is undefined.

Third-party middleware

npm install cors morgan helmet
app.use(cors());          // allow cross-origin requests from the frontend
app.use(helmet());        // sensible security headers
app.use(morgan("dev"));   // pretty request logs

Custom middleware: request logger

function requestLogger(req, res, next) {
  const start = Date.now();
  res.on("finish", () => {
    console.log(`${req.method} ${req.url} ${res.statusCode} ${Date.now() - start}ms`);
  });
  next();
}

app.use(requestLogger);

Error-handling middleware

// 4 arguments mark this as an error handler
app.use((err, _req, res, _next) => {
  console.error(err);
  res.status(500).json({ error: "Internal Server Error" });
});

Register error middleware last, after all routes.

Why middleware order matters

  • express.json() must run before any route that reads req.body
  • Auth middleware runs before protected routes
  • Validation middleware runs after body parsing, before the handler
  • Error middleware sits at the very end of the pipeline

Part 4

Validation and DTOs

Never trust input. Validate at the boundary, then pass clean, typed data inward.

Why validate at the boundary?

  • HTTP bodies are unknown — anything can arrive
  • Reject bad input fast with a clear 400 response
  • Keep validation rules in one place, reusable across routes
  • Same Zod library you used in Week 4 with react-hook-form

Install Zod on the server

npm install zod

Define a request schema

import { z } from "zod";

export const createMeetingSchema = z.object({
  title: z.string().min(3, "Title must be at least 3 characters"),
  date: z.string().datetime(),
  host: z.string().min(1),
  participants: z.array(z.string().email()).default([]),
});

Reusable validate middleware

import { ZodSchema } from "zod";
import { Request, Response, NextFunction } from "express";

export const validate =
  (schema: ZodSchema) =>
  (req: Request, res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({ error: result.error.flatten() });
    }
    req.body = result.data;  // typed and clean
    next();
  };

app.post("/meetings", validate(createMeetingSchema), handler);

Data Transfer Objects (DTOs)

  • A DTO is the shape carried between layers (HTTP <-> service <-> DB)
  • Keeps the wire format separate from internal domain types
  • Lets you evolve internals without breaking clients

DTO from a Zod schema

export type CreateMeetingDto = z.infer<typeof createMeetingSchema>;

function createMeeting(dto: CreateMeetingDto): Meeting {
  return {
    id: crypto.randomUUID(),
    title: dto.title,
    date: dto.date,
    host: dto.host,
  };
}

One schema gives you runtime validation and the compile-time type — no duplication.

Part 5

Databases and ORMs

Where the data lives after the request ends.

What is a database?

  • Durable structured storage with a query API
  • Survives server restarts and scales beyond in-memory state
  • Models concurrency: many requests reading/writing safely

Relational (SQL) databases

  • Examples: PostgreSQL, MySQL, SQLite
  • Strict schemas with tables, columns, and types
  • Joins across related tables, ACID transactions
  • Great default for most business apps

Document (NoSQL) databases

  • Example: MongoDB
  • Documents are flexible JSON-like blobs
  • Easy to evolve shape; weaker cross-document joins
  • Fits content/catalog data and prototypes

Key-value stores

  • Example: Redis
  • Very fast lookups by key
  • Used for caching, sessions, rate limiting, queues

Other shapes (briefly)

  • Graph (Neo4j) — relationship-heavy data like social graphs
  • Search (Elasticsearch, OpenSearch) — full-text and faceted search
  • Time-series (InfluxDB) — metrics, IoT

How to pick a database

  • Shape of data: rows + relations? documents? key-value?
  • Read vs write patterns and scale targets
  • Consistency needs (transactional vs eventual)
  • Team familiarity and hosting options

For Basum we will use a relational DB (PostgreSQL) later.

What is an ORM?

  • Object-Relational Mapper — maps DB rows to typed objects
  • Generates queries, manages connections, supports migrations
  • Lets you stay in TypeScript instead of writing raw SQL strings

ORM landscape (Node)

  • Prisma — schema file, generated client, great DX (recommended starter)
  • Drizzle — TypeScript-first, close to SQL, lightweight
  • TypeORM / Sequelize — older, decorator/active-record style

ORM vs raw SQL

ORM

  • Faster CRUD, typed results
  • Migrations and tooling
  • Abstracts SQL — can hide perf issues

Raw SQL

  • Full control and tuning
  • No mapping layer
  • More boilerplate and manual types

Most teams start with an ORM and drop to raw SQL for the hot 5%.

Part 6

Hello-World Demo

Build a tiny Express + TypeScript server from zero. Same steps as Class 1 hands-on.

Step 1 — Project init

mkdir basum-api
cd basum-api
npm init -y

Add "type": "module" in package.json to use ESM imports.

Step 2 — Install dependencies

npm install express zod
npm install -D typescript tsx @types/node @types/express

Step 3 — tsconfig.json

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "outDir": "dist",
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}

Step 4 — src/server.ts

import express from "express";

const app = express();
app.use(express.json());

app.get("/", (_req, res) => {
  res.json({ message: "hello world" });
});

app.listen(3000, () => {
  console.log("listening on http://localhost:3000");
});

Step 5 — Run with tsx

npx tsx watch src/server.ts

Then open http://localhost:3000 in the browser.

Step 6 — Add a /health endpoint

app.get("/health", (_req, res) => {
  res.json({ status: "ok", uptime: process.uptime() });
});

Health endpoints are the simplest way to verify the server is alive.

Step 7 — Try it with curl

curl http://localhost:3000/
# { "message": "hello world" }

curl -i http://localhost:3000/health
# HTTP/1.1 200 OK
# { "status": "ok", "uptime": 4.21 }

Verify the demo

  • Server logs "listening on http://localhost:3000"
  • / returns the hello-world JSON
  • /health returns { status: "ok" }
  • Unknown path returns Express default 404

Done when: both endpoints respond with valid JSON.
