Assignment 1 - Basum API (Express + TypeScript + Zod)

Build a small but real REST API for Basum meetings. Use Express, TypeScript, and Zod from the session.

Endpoints

  • GET /meetings - return all meetings (in-memory store is fine for this week)
  • GET /meetings/:id - return one meeting, 404 when missing
  • POST /meetings - create a meeting; validate body with Zod
  • PATCH /meetings/:id - partial update; validate body with a separate schema
  • DELETE /meetings/:id - delete; respond 204 No Content

Requirements

  • Use strict: true in tsconfig.json; no any in your code.
  • Define createMeetingSchema and updateMeetingSchema in Zod.
  • Export DTO types using z.infer<typeof ...> and use them in handlers.
  • Implement a reusable validate(schema) middleware (one for body, optionally one for params).
  • Add a request-logger middleware (method url status durationMs).
  • Add a final error-handling middleware with the 4-arg signature.
  • Use express.json() before any route that reads req.body.

Checklist

  • Server starts with npm run dev and prints a listen URL.
  • All five endpoints work via curl or Postman.
  • Invalid POST/PATCH bodies return 400 with the Zod error shape.
  • Missing meeting on GET/PATCH/DELETE returns 404.
  • Logger prints exactly one line per request.
  • Throwing in a route is caught by the error middleware and returns a JSON 500.

Assignment 2 - REST vs GraphQL note

Add a README section (8-12 lines) named "REST vs GraphQL for Basum".

  • Summarize 2 pros and 2 cons of each style in your own words.
  • Choose either REST or GraphQL for Basum and justify the choice in 2-3 sentences (think about the client, caching, and team).
  • Optional: name one situation where you would switch styles in the future.

Checklist

  • README contains a clearly labeled "REST vs GraphQL" section.
  • Both pros and cons are listed for each style.
  • A clear decision is stated with reasoning.

Assignment 3 - Database + ORM exploration

No real database connection is required this week. Pick one ORM (Prisma or Drizzle) and answer in a README section called "Basum data model".

  • In 6-10 lines, describe how you would model the meetings table (columns, types, primary key).
  • Include at least one column with a constraint (for example: title NOT NULL, email UNIQUE, or date with a CHECK).
  • Write one sentence on which database engine you would use (PostgreSQL, MySQL, SQLite, MongoDB, …) and why.
  • Optional: paste a sketch of the Prisma schema.prisma or Drizzle table definition.

Checklist

  • README contains a "Basum data model" section.
  • Columns, types, and primary key are described.
  • At least one column has an explicit constraint.
  • A database engine is named with a one-sentence reason.
