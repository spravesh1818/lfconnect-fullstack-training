Part 1

Authentication Mental Model

Authentication answers: who is this user? Authorization answers: what can they do?

Typical SPA login flow

  1. User submits email/password on /login
  2. Backend validates credentials
  3. Backend returns JWT + user profile
  4. Client stores token and attaches it to API requests
  5. Protected pages read auth state before rendering

What is a JWT?

  • Compact signed string: header.payload.signature
  • Payload often includes sub, exp, roles
  • Server verifies signature — client cannot trust payload alone

Decode for display only; security decisions belong on the server.

localStorage for teaching demos

Pros

  • Simple to implement in SPA labs
  • Survives page refresh

Cons

  • Readable by any XSS script
  • Not httpOnly — production often prefers secure cookies

Never store passwords in localStorage — only token + minimal user info.

AuthProvider sketch

export function AuthProvider({ children }) {
  const [token, setToken] = useState(() => localStorage.getItem("access_token"));
  const [user, setUser] = useState(() => readStoredUser());

  const login = async (email, password) => {
    const res = await loginRequest(email, password);
    localStorage.setItem("access_token", res.token);
    localStorage.setItem("auth_user", JSON.stringify(res.user));
    setToken(res.token);
    setUser(res.user);
  };

  const logout = () => {
    localStorage.removeItem("access_token");
    localStorage.removeItem("auth_user");
    setToken(null);
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, token, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

useAuth hook

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within AuthProvider");
  return ctx;
}

Wrap AuthProvider around BrowserRouter or inside it so routes can consume auth.

Login page

const { login } = useAuth();

Attach Bearer token to fetch

const { token } = useAuth();

const res = await fetch(`${import.meta.env.VITE_API_URL}/meetings`, {
  headers: {
    Authorization: token ? `Bearer ${token}` : "",
    "Content-Type": "application/json",
  },
});

If API returns 401, call logout() and send user to /login.

Handle token expiry

  • Backend should return 401 when token is invalid/expired
  • Client clears storage and redirects to login
  • Optional: decode JWT exp client-side for early logout warning

Verify auth flow

  • Login with demo credentials → dashboard visible
  • Refresh page → still logged in (token restored from localStorage)
  • Logout → token removed, protected pages blocked

Part 3

Private Routes

Client-side guards improve UX; backend must still enforce authorization.

ProtectedRoute component

import { Navigate, useLocation } from "react-router";

export default function ProtectedRoute({ children }) {
  const { token } = useAuth();
  const location = useLocation();

  if (!token) {
    return <Navigate to="/login" replace state={{ from: location }} />;
  }

  return children;
}

Wire into route table

<Route path="/login" element={<LoginPage />} />

<Route element={<ProtectedRoute><AppShell /></ProtectedRoute>}>
  <Route path="/" element={<Dashboard />} />

Part 4

Auth Best Practices

Do and do not

  • Do validate JWT on every protected API route (server)
  • Do use HTTPS in production
  • Do keep tokens out of URLs and git
  • Do not trust client-only checks for sensitive actions
  • Do not store passwords in localStorage

Production patterns (overview)

  • Short-lived access token + refresh token rotation
  • httpOnly, Secure, SameSite cookies for session tokens
  • CSRF protection when using cookies
  • Role-based access checks on server, not only hidden buttons

Environment config

# .env.local
VITE_API_URL=https://api.example.com
fetch(`${import.meta.env.VITE_API_URL}/login`, …)

Set the same keys in Netlify before production builds.

Part 6

Next.js Teaser

Same React components — different framework responsibilities.

Vite SPA vs Next.js

Vite + React SPA

  • Client-side routing (React Router)
  • Static deploy (Netlify)
  • Great for dashboards and internal tools

Next.js

  • File-based routing in app/ or pages/
  • SSR, SSG, and API routes built-in
  • Strong for SEO and full-stack React

Rendering modes (one line each)

  • CSR: render in browser after JS loads (typical SPA)
  • SSR: HTML generated per request on server
  • SSG: HTML generated at build time

When teams pick Next.js

  • Marketing pages need SEO
  • Auth/session logic on server
  • Colocate API endpoints with UI

Your Meeting Basum skills transfer — routing and data patterns feel familiar.
