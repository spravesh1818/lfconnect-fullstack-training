Part 1

Authentication Landscape

Authentication — who is this user? Authorization — what may they do?

Analogy: your ID card proves identity (authN); your building badge grants floor access (authZ).

Common authentication types

  • Session cookies — server stores session id; browser sends cookie automatically. Classic server-rendered web apps.
  • JWT (Bearer tokens) — signed token in Authorization header. SPAs, mobile apps, APIs. Week 4 client + Week 7 server.
  • OAuth 2.0 / OIDC — “Login with Google/GitHub.” Delegate identity to a provider. SaaS and social login.
  • API keys — long-lived secret for scripts, webhooks, service-to-service. Not for human passwords.
  • Magic links / OTP — passwordless email or SMS one-time codes.
  • MFA — second factor (TOTP app, SMS) on top of any method above.

When to use which?

  • Same-site browser app — httpOnly session cookies (CSRF protection required)
  • SPA + REST API — JWT Bearer tokens (watch XSS on client storage)
  • Third-party login — OAuth/OIDC; you trust Google/GitHub to verify identity
  • CI pipeline / cron job — API keys with scoped permissions and rotation
  • High-security accounts — password + MFA regardless of token type

Stateful vs stateless

Stateful (sessions)

  • Session stored in Redis or DB
  • Easy to revoke instantly
  • Server must look up session each request

Stateless (JWT)

  • Token carries signed claims
  • Scales horizontally without shared session store
  • Revocation needs extra work (blocklist, short TTL)

Where auth lives

  • Client guards (Week 4 React Router) — hide pages, improve UX
  • Server middleware (Week 7) — enforce who may call each API route

Anyone can call your API with curl or Postman. Server enforcement is what actually secures data.

Part 3

Backend Auth Mental Model

Week 4 taught client-side JWT storage. Today we implement the server side.

Week 4 vs Week 7

  • Week 4 — JWT stored in React localStorage; client-side route guards
  • Week 7 — server verifies JWT on every protected API route

Client guards improve UX. Server enforcement is what actually secures data.

Server login flow

  1. Client POSTs email + password to /auth/login
  2. Server finds user, compares password hash
  3. Server signs JWT with secret, returns { token, user }
  4. Client sends Authorization: Bearer <token> on protected requests
  5. Server middleware verifies token before running handler

Never store plain passwords

// BAD — never do this
{ email: "a@b.com", password: "secret123" }

// GOOD — store hash only
{ email: "a@b.com", passwordHash: "$2a$10$..." }

Use bcrypt.hash on register; bcrypt.compare on login.

Part 4

Auth Module

Same DDD layout as todos: model, schema, service, controller, routes under auth/.

Auth routes

  • POST /auth/register — create user, return profile (no password)
  • POST /auth/login — return JWT + user profile

Status codes: 201 register, 200 login, 401 bad credentials, 409 email taken.

Sign JWT on login

const token = jwt.sign(
  { sub: user.id },
  process.env.JWT_SECRET,
  { expiresIn: "7d" }
);

sub = subject (user id). Keep JWT_SECRET in .env.

requireAuth middleware

const header = req.headers.authorization;
if (!header?.startsWith("Bearer ")) {
  return res.status(401).json({ error: "Missing token" });
}
const token = header.slice("Bearer ".length);
const payload = jwt.verify(token, JWT_SECRET);
req.userId = payload.sub;
next();

Part 5

Protect Routes

Apply requireAuth before handlers that change data.

Suggested policy for Todo API

  • Public: GET /todos, GET /todos/:id
  • Protected: POST, PUT, PATCH, DELETE on todos

Anyone can browse; only logged-in users can create or edit.

Test the full flow

POST /auth/register  → 201
POST /auth/login     → { token, user }
POST /todos + Bearer token → 201
POST /todos (no token)     → 401
