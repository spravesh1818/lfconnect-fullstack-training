Part 2

Why Cache?

Store a copy of expensive or frequent data in fast storage so the next read is cheaper.

Cache hit vs cache miss

  • Hit — data found in cache; skip database query
  • Miss — data not in cache; read from DB, then write to cache

Benefits: lower latency, less DB load, lower cloud cost at scale.

Caching layers

  • Browser cache — static assets (Week 1)
  • CDN / edge — HTML, images, API responses close to users
  • Application cache — Redis in your Node server (today)
  • Database query cache — built into some DBs; different concern

Today we focus on application-level caching you control in Express.

Part 3

Redis

In-memory key-value store. Extremely fast reads/writes. Used for cache, sessions, rate limits, and job queues.

Run Redis locally

docker run -p 6379:6379 redis:7-alpine

Add to .env: REDIS_URL=redis://localhost:6379

Core commands: SET key value EX 60, GET key, DEL key

Node client — ioredis

import Redis from "ioredis";

export const redis = new Redis(process.env.REDIS_URL);

redis.on("connect", () => console.log("Redis connected"));
redis.on("error", (err) => console.error("Redis error", err));

Part 4

Cache-Aside Pattern

The application checks cache first, falls back to DB, then populates cache. Most common pattern for REST APIs.

Read path — GET /todos

const key = "todos:list";
const cached = await redis.get(key);
if (cached) {
  console.log("CACHE HIT");
  return JSON.parse(cached);
}

const todos = await todoService.findAll();
await redis.set(key, JSON.stringify(todos), "EX", 60);
return todos;

EX 60 = TTL 60 seconds. Data expires automatically if you forget to invalidate.

Invalidation on writes

When todos change, delete the cache key so the next GET rebuilds from MongoDB.

// After create, update, or delete:
await redis.del("todos:list");

Rule: every write path that affects cached data must invalidate (or update) the cache.

Good class example

  • GET /todos — read-heavy, many repeated requests
  • Short staleness OK (list might be 60s old in a demo app)
  • Easy to verify: second request logs CACHE HIT

Part 5

When NOT to Cache

Caching is a tradeoff. Wrong caching causes bugs worse than slow queries.

Do not cache these

  • Financial balances — stale balance = angry users or money lost
  • Inventory / seat counts — overselling events or products
  • Auth revocation lists — logged-out tokens must fail immediately
  • Highly personalized per-user data — cache key explosion, low hit rate
  • Write-heavy endpoints — invalidation complexity exceeds benefit
  • Strong consistency requirements — user must always see latest
  • Large files / images — use object storage + CDN, not Redis strings

Anti-patterns

  • “Cache everything” without measuring — premature optimization
  • No TTL and no invalidation — stale data forever
  • Caching errors or empty results — error cached for 60s
  • Same cache key for different users' private data — data leak risk

TTL guidance

Pick TTL based on how stale data your business tolerates.

  • Public event listings — 30–120 seconds might be fine
  • User profile — often skip cache or use very short TTL + invalidation
  • Never rely on TTL alone when correctness matters — invalidate on writes

Session Summary

  • Cache-aside: check Redis → DB on miss → set with TTL
  • Invalidate on every write that affects cached reads
  • Redis is fast; use it for small JSON blobs, not giant files
  • Skip caching when correctness or personalization dominates
